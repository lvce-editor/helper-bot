# Repository configuration coverage

The schema is intentionally explicit rather than passing arbitrary Settings-app data to GitHub. The [Settings app reference](https://github.com/repository-settings/app/blob/master/docs/configuration.md) lists repository, branches, labels, milestones, collaborators, teams and environments. Each is accounted for below. This manager applies trusted PR data **before merge**, after validating the entire PR matrix, rather than synchronizing any author's default-branch commit.

## Current installation and permission blockers

Verified on 2026-10-11: App 755618 has administration/actions/contents/pull_requests/workflows write, checks/metadata read. Its existing **pull_requests write** permission also permits label and milestone management. Environment and ruleset writes also use its existing **administration write** permission. It lacks **organization members read** and **pages write**, so team-grant and Pages configuration fail permission preflight before resource reads or writes. An installation administrator must add and approve those permissions before opting those sections in. Pages update requires both administration write and pages write. This implementation does not change the App's permissions or use a maintainer token as a substitute. The trusted Actions job remains read-only and validates data and CI; the App checks its own authoritative installation permissions before applying.

## Ownership, reconciliation and recovery

Omitted sections and keys are unmanaged. Bootstrap a snapshot matching live state on main first. `settings` keys and managed branch/protection keys cannot change ownership in an application PR. Collection sections can be bootstrapped as `[]`, after which trusted PRs may add/remove entries. Topics own the full set. Collections own only identities present in base or desired: unrelated labels, milestones, environments and grants remain untouched. Resource names are stable identities, not rename directives. Removing a managed label/milestone/environment deletes it, including GitHub's associated effects; do not represent renames as delete/create unless that is intended.

Before any settings writes, permission checks and all managed live snapshots must match base or desired. Writes run serially under the existing distributed repository lock, with PR head/base rechecked between resources. Administrative endpoint success is followed by effective-state reads. GitHub provides no transaction across these endpoints: a partial failure is reported, and an exact-head retry skips resources already at desired state. External administration must be serialized; the lock cannot exclude unrelated API clients. An uncertain response requires live reconciliation before retrying. Pending invitations and inherited-access effects are explicit failures. Abandoned PR changes persist; no automatic rollback.

YAML is bounded to 64 KiB, rejects duplicate mapping keys, aliases, unknown tags/fields and invalid resource schemas. JSON is accepted only as the legacy `.github/repository-config.json` file during migration. Remove it when adding `.github/repository-config.yml`; having both is ambiguous and rejected. Base JSON to head YAML is supported with identical managed ownership. Do not add new managed ownership during that automatic application; merge a reviewed bootstrap snapshot first.

## Complete repository rulesets

`rulesets` owns complete repository ruleset definitions: `name`, `target` (`branch`, `tag`, `push`), `enforcement` (`active`, `disabled`, `evaluate`), `conditions`, `bypass_actors`, and `rules`, including each rule's parameters. The strict nested schema comes from GitHub's [create repository ruleset endpoint](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset). All rule types in that schema are accepted; unknown fields/types fail closed. GitHub plan, repository visibility, target/rule compatibility and actor eligibility restrictions still apply. For example, evaluation requires Enterprise, and push rulesets require an eligible private/internal repository. An API rejection remains a failure, never an equivalent substituted rule.

The checked-in schema is generated from [github/rest-api-description revision 58b1e0c00b39b9e46c24dc4a0ba6a2669c90e9c1](https://github.com/github/rest-api-description/blob/58b1e0c00b39b9e46c24dc4a0ba6a2669c90e9c1/descriptions/api.github.com/api.github.com.json). To update, download a reviewed revision, run `node scripts/generateRepositoryRulesetSchema.js /path/to/api.github.com.json`, format the output, and update this revision reference. No remote schema is fetched at runtime. Unknown keys are rejected at every object level; complete top-level definitions, unique rule types, and unique case-insensitive names are required.

Experimental/undocumented fields absent from that public write schema cannot be expressed yet. For example, live helper-bot ruleset 11990826 returns `pull_request.parameters.require_extra_approval_for_unattributed_changes`, which is absent from GitHub's published create schema. Such live parameters cause a snapshot conflict rather than being silently erased. Keep that ruleset under the existing partial `rulesetId` adapter until GitHub documents the field and the pinned schema is updated.

Bootstrap `rulesets: []` on main to manage new rulesets, or bootstrap explicit complete snapshots matching existing live definitions. Names are stable identities resolved to numeric API IDs; IDs are not accepted in YAML. Matching organization/inherited rulesets, duplicate names and overlap with `rulesetId` are rejected. An omitted section is unmanaged; an empty list removes only rulesets previously owned by the base configuration. Removing an entry deletes that ruleset. A rename is an explicit delete/create. Other repository and organization rulesets remain untouched. Whole-rule parameters and bypass actors are replaced only within explicitly owned definitions; include effective API defaults in snapshots when GitHub returns them.

The existing `requiredStatusChecks` gate continues to manage main's classic protection or the separate legacy `rulesetId`. Full ownership cannot overlap that legacy ID. This prevents whole-ruleset removal, enforcement/condition/bypass changes from weakening the mandatory CI gate. Every managed `required_status_checks` rule must contain the complete intended PR matrix and integration ID 15368; checks cannot be dropped or assigned to another provider. Trusted author login/immutable ID, successful exact-head/base CI, immutable main, distributed lock, all-resource preflight and PR rechecks remain required. Creates/updates are read back by ID; removals require a subsequent 404. A lost create response is reconciled by stable name on retry.

```yml
rulesets:
  - name: Protect release tags
    target: tag
    enforcement: active
    conditions:
      ref_name:
        include: ['refs/tags/v*']
        exclude: []
    bypass_actors: []
    rules:
      - type: deletion
      - type: non_fast_forward
```

## Pages and requested general settings

`pages` accepts the [update Pages endpoint](https://docs.github.com/en/rest/pages/pages#update-information-about-a-github-pages-site) fields: `build_type` (`workflow` for GitHub Actions, `legacy` for branch publishing), `source` (`branch` plus `path`, `/` or `/docs`), `cname` (hostname or null), and `https_enforced` (boolean). Bootstrap the managed keys against an existing site's live state on main; keys cannot be added or removed in an application PR. Omitted keys stay unmanaged. Sites are not implicitly created or deleted. Domain verification, certificates and publishing workflows are separate GitHub prerequisites. Effective values are read back before reporting success. Even an unchanged managed Pages section requires the App's Pages permission; an unavailable capability cannot be claimed as integration-tested.

```yml
pages:
  build_type: workflow
settings:
  has_wiki: false
  has_projects: false
  allow_squash_merge: true
  allow_merge_commit: false
  allow_rebase_merge: false
  allow_auto_merge: true
  delete_branch_on_merge: true
```

Each general setting above already maps directly to [update repository](https://docs.github.com/en/rest/repos/repos#update-a-repository) and is confirmed through get repository after writes. These keys also require reviewed main bootstrap.

GitHub's **Limit how many branches and tags can be updated in a single push** is a per-push count, not a lifetime branch/tag limit or a push ruleset. [GitHub documents this setting in the General settings UI](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-the-push-policy-for-your-repository), recommending a maximum of five updates. As of 2026-10-11 neither the public REST update-repository schema nor the live GraphQL `UpdateRepositoryInput` exposes this setting. There is no supported YAML field/API mapping for it; unknown proposed settings fail validation. It requires repository-admin UI configuration until GitHub publishes a supported API. The bot does not automate GitHub's private browser endpoint or substitute creation/deletion restrictions for this count.
